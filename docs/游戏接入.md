# 游戏接入指南（mod 作者看这份）

大脑是本地 Python 服务器（默认 `http://127.0.0.1:8765`），任何能发 HTTP 的游戏都能接。
**字段级契约见 [`API.md`](./API.md)**；这份只讲怎么接、要注意什么。

## 0. 心智模型：动作 = LLM 直接调用的工具

```
玩家说话 ──► POST /api/talk
                 │
                 ▼
        LLM 自己决定调什么工具（记忆工具 + 你声明的动作）
                 │  动作工具
                 ▼
        大脑 POST 你的 execute_url（同步，做完才回响应）
                 │
                 ▼
        结果作为"工具消息"回到上下文 ──► LLM 继续说台词（delta 帧）
                 │
                 ▼
        结果当场写进记忆卡（你不需要为它做任何事）
```

要点：

- **你不主动推动作**。动作由 LLM 在回合内调用，大脑同步转发给你的 `execute_url`；
  一次 `/api/talk` 里同一动作可能被调用多次（多轮工具调用）。
- **动作工具只有你报到声明过的才存在**（白名单唯一闸门，见 §1）。
- **同步路径不用回报**：`status: "done"` 的结果大脑当场写卡。`/api/action_result` 只给**长动作**用。
- **台词只走 `delta` 帧**；流末尾的 `action` 帧只是"本回合已执行的动作"的记录（带 `ok/status/call_id`），
  **mod 不需要照它做任何事**。

## 1. 报到（必须）

启动时（并建议每 20~30 秒重报一次当心跳）POST `/api/capabilities`：

```bash
curl -X POST http://127.0.0.1:8765/api/capabilities -H "Content-Type: application/json" -d '{
  "mod": "mygame",
  "execute_url": "http://127.0.0.1:8766/execute",
  "actions": [
    {"name": "cook", "desc": "用厨房做饭", "params": {"dish": "菜名(字符串)"}},
    {"name": "goto", "desc": "走到某地",   "params": {"place": "地点名(字符串)"}}
  ]
}'
```

- `execute_url` **不填 = 你没有可执行的动作**，动作工具不会进 LLM 工具定义（可以只用心智/记忆功能）。
- 心跳超时默认 60 秒（`NPC_MOD_HEARTBEAT_TIMEOUT`）：超时视为离线，大脑不再调你的动作。
  捎带 `mod` 的 `/api/talk`、`/api/action_result` 也算心跳，但别指望它们替你保活。
- 参数目前一律按字符串传（`params` 里写的是给 LLM 看的说明）；类型/范围校验尚未做（见 §6）。

## 2. 实现执行接口 `execute_url`

收到请求 → 执行 → 回响应：

```json
// 大脑 → 你
{"npc_id": "cang", "action": "cook", "params": {"dish": "面"},
 "mod": "mygame", "call_id": "9f2c8b1e4d5a47c3b0e6f7a8c9d0e1f2"}

// 你 → 大脑（当场做完）
{"ok": true,  "status": "done", "note": "面煮好了"}

// 你 → 大脑（长动作：先收下，稍后异步回报）
{"ok": false, "status": "running", "note": "还在灶上"}
```

- **失败必须用 `ok: false`**：`status` 里没有"失败"这个值（`done` / `running` 之外的值一律按 `done` 处理）。
- `note` 会进记忆卡，写清"做成了什么"，别写调试信息。
- 请求处理要**幂等**（见 §3）。

### 长动作（`status: "running"`）

1. 把请求里的 `call_id` 存下来（连同 npc/参数一起）。
2. 立刻回 `{"ok": false, "status": "running"}` —— 不要说"做完了"。
3. 做完了再 POST `/api/action_result`，把 `call_id` **原样带回**：

```bash
curl -X POST http://127.0.0.1:8765/api/action_result -H "Content-Type: application/json" -d '{
  "npc_id": "cang", "action": "cook", "ok": true, "note": "面煮好了",
  "call_id": "9f2c8b1e4d5a47c3b0e6f7a8c9d0e1f2", "mod": "mygame"
}'
```

- 带回 `call_id` → 大脑**精确销账**（同一 NPC 同名动作并发也不会串），响应 `matched: true`。
- 回报时 `note` 可以省略：大脑会用登记下来的 `params` 补一句描述。
- **同一个 `call_id` 只能回报一次**：重复回报 `matched: false` 且**不写卡**（防止同一次动作写两条记忆）。

## 3. 对 `call_id` 幂等（对你的要求）

大脑侧无法强制，只能约定 —— 请这样做：

- **按 `call_id` 记去重表**：重复收到同一个 `call_id` 的动作请求，**不重复执行**，直接返回上次的结果
  （`done` 的返回上次的 `ok/note`；还在做的返回 `running`）。
- **保留最近几百条**（例如 200~500 条，或至少覆盖 `NPC_PENDING_TTL`，默认 120 秒）即可，`call_id` 是
  32 位 hex 的随机串，不会撞，但表无限增长也没必要。
- 为什么要幂等：LLM 可能重试同一个动作（说错了一次、上下文重发），网络也可能重放；
  没有 `call_id` 时大脑无法去重，**你的游戏世界会被执行两次**。

## 4. 超时与失败语义

| 情况 | 大脑行为 | 你该怎么做 |
|---|---|---|
| 你回 `done` 且 `ok: true` | 当场写卡 `完成: <note>` | 正常 |
| 你回 `done` 且 `ok: false` | 当场写卡 `没做成: <note>` | 失败就用它 |
| 你回 `running` | 不写卡，登记待定 | 存 `call_id`，做完回报 |
| 大脑同步等待超时（`NPC_EXECUTE_TIMEOUT`，默认 30s） | **不当成失败**（你可能已经做了），不写卡，登记待定；LLM 被告知"没等到回应，不确定是否已经做成" | 请求可能仍在处理 → 照样做完并**带 `call_id` 回报** |
| 连不上你 / 你的响应不是 JSON 对象 | 当场写失败卡（请求大概率没到） | 检查 `execute_url` 与端口 |
| 登记后 `NPC_PENDING_TTL`（默认 120s）内一直没回报 | 写一条 `没做成: 一直没等到结果` | 超长动作请先回 `running`，别让大脑干等 |

所以：**动作可能执行超过 30 秒时，先回 `running`**，别硬扛同步等待 —— 大脑等不到就不知道你做没做，
只能过 TTL 才敢写"没做成"。

## 5. 完整示例时序

玩家说"你能帮我做顿饭吗"，`cook` 是个需要一会儿的长动作：

```
① 玩家 → 大脑     POST /api/talk  {"npc_id":"cang","mod":"mygame","message":"你能帮我做顿饭吗"}
② 大脑 → LLM      第一轮：模型决定调工具 cook(dish=面)
③ 大脑 → mod      POST http://127.0.0.1:8766/execute
                  {"npc_id":"cang","action":"cook","params":{"dish":"面"},
                   "mod":"mygame","call_id":"9f2c8b1e4d5a47c3b0e6f7a8c9d0e1f2"}
④ mod → 大脑      {"ok":false,"status":"running","note":"还在灶上"}
⑤ 大脑            登记 pending[9f2c...]（不写卡）
⑥ 大脑 → LLM      工具消息："cook 还在进行中，结果稍后才出来" → 模型继续说话
⑦ 大脑 → 玩家（SSE） data: {"type":"delta","text":"行啊，"}
                     data: {"type":"delta","text":"灶上煮着呢，等我一会儿。"}
                     data: {"type":"action","action":{"name":"cook","params":{"dish":"面"},
                            "ok":false,"status":"running","call_id":"9f2c8b1e..."}}
                     data: {"type":"done"}
⑧ mod（几分钟后，面真的煮好了）→ 大脑
                  POST /api/action_result
                  {"npc_id":"cang","action":"cook","ok":true,"note":"面煮好了",
                   "call_id":"9f2c8b1e...","mod":"mygame"}
⑨ 大脑            销掉 pending[9f2c...] → 记忆卡多一条「完成: 面煮好了」（matched: true）
                  {"ok":true,"npc_id":"cang","entry":{...},"matched":true}
⑩ 下次玩家说话     这轮对话起，记忆卡里"面煮好了"已经在上下文里（recall 能回忆到）
```

以上每一步都能用 `curl` 复现（③④ 由大脑发出，可以用 `python -m http.server` 之类的假执行接口顶上，
或直接在控制台「Mod / 能力」页模拟报到 + 「试对话」页看帧）。

## 6. 还没有的（别按这些写代码）

- **参数类型/范围**：`params` 全是字符串、大脑不校验（缺参、越界都照发），等 `/api/capabilities`
  扩展参数声明（类型 / 枚举 / 范围）之后再说。
- **长轮询传输**（游戏进程内的 Python mod 无法开放端口时，由 mod 主动拉动作）：未做。
- **动作并发**：同一回合的多个动作现在**串行**执行，每个最长等 `NPC_EXECUTE_TIMEOUT`。
- **`execute_url` 的安全**：地址由调用方自报，仅限本机使用；对外暴露前需要鉴权与地址校验。
- **打断 / 释放锁**：同步等你的动作期间，该 NPC 的锁一直被占着，新消息与回报会排队（等产品行为定）。
